OAuth Domain-Authorized Issuer Trust Method

Abstract

This document defines the Domain-Authorized Issuer (DAI) Trust Method: a subject_namespace_authorization Trust Method for the OAuth Identity Assertion Trust Framework in which the owner of a subject namespace (typically a DNS domain) publishes a policy listing the OAuth authorization servers it authorizes to assert identities in that namespace. The mechanism uses the DNS-based authority-publication pattern operators already deploy for CAA, MTA-STS, SPF, and DKIM. A Resource Authorization Server uses the published policy to verify that an identity assertion's issuer is authorized for the asserted subject namespace.¶

The lookup defined by this document is verifier-side: given an identity assertion in hand, the Resource Authorization Server locates the Subject Authority's issuer authorization policy. Client-side discovery of which Assertion Issuer to use before an assertion exists is a separate use case and is deferred to future work.¶

This document also defines the Issuer Authorization Policy wire format that the Trust Method consumes. The parent trust framework specification owns the generic Trust Policy document, Trust Method category structure, cross-category combination rule, and Subject Authority Determination concept.¶

1. Introduction

OAuth deployments using identity-assertion grants need to answer "is this Assertion Issuer authorized to assert about subjects in this namespace?". Such grants include the Identity Assertion JWT Authorization Grant (ID-JAG) and generic JWT-bearer assertions carrying an identity claim ([TRUST-FRAMEWORK]). Federation membership authenticates an issuer but does not by itself entitle it to assert about any particular namespace. Only the namespace owner can authoritatively delegate that.¶

The Domain-Authorized Issuer (DAI) Trust Method lets the owner of a DNS-namable subject namespace publish, in DNS, the Assertion Issuers it authorizes for its namespace. The DNS record lists the issuers inline or points at an HTTPS-hosted JSON document. That document carries richer policy: validity windows, format restrictions, and tenant binding. A Resource Authorization Server that does not take issuers or a policy location from DNS can instead fetch the policy from a dedicated HTTPS host, oauth-issuer-policy.{domain}. Either way, the DNS record is the Subject Authority's explicit opt-in. A namespace that publishes no record is not covered.¶

Authority is established by control of the publication channel: whoever can publish at _oauth-issuer-policy.{domain} is the Subject Authority for {domain}. The pattern follows CAA [RFC8659], MTA-STS [RFC8461], SPF, and DKIM (Appendix A.1).¶

A Resource Authorization Server applies DAI when it verifies an identity assertion: the Subject Authority's published policy decides whether the asserting issuer is authorized for the subject's namespace.¶

DAI is non-transitive: a Subject Authority directly lists each Assertion Issuer it authorizes ([TRUST-FRAMEWORK] §Transitive Authorization is Bounded).¶

DAI is also independent of OpenID Federation: a Subject Authority can publish DAI records and a Resource Authorization Server can evaluate them without any federation infrastructure.¶

1.1. Relationships

DAI is a subject_namespace_authorization Trust Method specification under [TRUST-FRAMEWORK]. The Trust Method's evidence is the Issuer Authorization Policy, in which the Subject Authority authorizes Assertion Issuers. The DNS record (or DNS pointer plus HTTPS document) is one publication channel for it.¶

Lookup state classification and fail-closed requirements follow [TRUST-FRAMEWORK] §Lookup States and Fail-Closed.¶

DAI extends [TRUST-FRAMEWORK], which owns the Trust Policy document format, Trust Method machinery, Subject Authority Determination, and OAuth grant-profile bindings. This document defines:¶

  • the Issuer Authorization Policy document (Section 3);¶

  • the DNS and HTTPS publication channels (Section 4.1);¶

  • the lookup procedure (Section 5);¶

  • the verification rules (Section 6); and¶

  • the domain_authorized_issuer Trust Method, with an HTTPS-only deployment variant (Section 8.2).¶

A bridge to the Email Verification Protocol's DNS records and a client-side discovery use case are sketched in Appendix B.¶

2. Terminology

This document uses these terms as defined in [TRUST-FRAMEWORK]:¶

  • Subject Authority: the owner of a subject namespace, such as the DNS domain acme.example for alice@acme.example.¶

  • Assertion Issuer: the authorization server that issues identity assertions, typically an organization's Identity Provider.¶

  • Resource Authorization Server: the authorization server that receives an identity assertion and decides whether to accept it.¶

  • Trust Policy: the document in which a Resource Authorization Server states the Trust Methods it requires.¶

  • Trust Method: a procedure for evaluating evidence about an Assertion Issuer.¶

  • Issuer Authorization Policy: the document in which a Subject Authority lists the Assertion Issuers it authorizes (Section 3).¶

  • Consumer: a party that retrieves and processes a policy document.¶

  • Decision-affecting member: a policy member whose value can change whether a consumer accepts an assertion.¶

Subject Identifier formats follow [RFC9493].¶

This document defines two terms:¶

Domain-Authorized Issuer (DAI):

The Trust Method defined here, in which a Subject Authority publishes, over DNS and HTTPS, the Assertion Issuers it authorizes for its namespace.¶

Publisher:

The Subject Authority, or a policy host acting for it, when it publishes a DNS record or an Issuer Authorization Policy.¶

3. Issuer Authorization Policy Document

The Issuer Authorization Policy is the evidence that DAI consumes. With it, a Subject Authority delegates to named Assertion Issuers the right to assert identities in its namespace. Each authorized_issuers entry is a delegation, which valid_from, valid_until, tenant, and subject_identifier_formats can constrain. If no current delegation matches the assertion (Section 6), the Assertion Issuer is not authorized for the asserted namespace, whatever other properties the assertion has.¶

The Issuer Authorization Policy is a JSON object served over HTTPS. Publishers MUST serve it with media type application/json; consumers additionally accept any media type using the structured +json suffix (Section 5.1). It has the following members:¶

subject_authority

REQUIRED. String. The Subject Authority identifier this policy applies to. For DNS-domain Subject Authorities the publisher MUST write this value in A-label (ASCII) form per [RFC5891], mirroring the authority= directive (Section 4.3). Consumers MUST verify this value matches the Subject Authority computed in [TRUST-FRAMEWORK] §Subject Authority Determination after applying the comparison rules for that Subject Authority form.¶

authorized_issuers

REQUIRED. JSON array of authorized issuer objects, which MAY be empty. An empty array is an explicit denial: retrieval is Affirmative (Section 5.1), but no entry can match (Section 6). Consumers MUST NOT fall through to any other channel on encountering a denial. Each object has:¶

issuer

REQUIRED. String. The Assertion Issuer identifier. For OAuth authorization server issuer identifiers, this value MUST be an absolute HTTPS URL with no query or fragment component ([RFC8414] Section 2). The URL MAY contain a path component.¶

The value and the JWT iss claim are compared by exact case-sensitive string equality (octet-for-octet), with no normalization, consistent with [RFC8414] issuer-identifier comparison: https://a and https://a/ are distinct issuers.¶

Issuer identifiers whose string form contains a ; cannot be expressed in the inline DNS form (Section 4.3) and MUST be published via the HTTPS document instead.¶

tenant

OPTIONAL. Non-empty string. The issuer-side tenant identifier authorized for this Subject Authority, corresponding to a top-level tenant claim carried by the assertion (in ID-JAG, [ID-JAG] §6.1). When present, the assertion's top-level tenant claim MUST be present and MUST exactly match this value using case-sensitive string comparison. An assertion that lacks the tenant claim or carries a different value does not match this entry.¶

When absent, the entry matches only assertions that carry no top-level tenant claim. Under a grant profile that carries no tenant claim, such as the generic JWT-bearer grant of [RFC7523], only entries that omit tenant can match (Section 9.9).¶

Tenant values are issuer-specific and MUST NOT be compared across issuers. To authorize multiple tenants of the same shared issuer, publish one entry per (issuer, tenant) pair.¶

subject_identifier_formats

OPTIONAL. JSON array of Subject Identifier format names ([RFC9493]) this Assertion Issuer is authorized for. If omitted, the Assertion Issuer is authorized for any format that resolves to this Subject Authority, including formats whose extraction procedures are registered after the policy is published.¶

valid_from

OPTIONAL. [RFC3339] date-time. The delegation MUST NOT be treated as valid before this time. A consumer MAY apply a clock-skew tolerance of at most 5 minutes, consistent with JWT nbf conventions ([RFC7519] Section 4.1.5). This tolerance applies only to valid_from and MUST NOT be applied to valid_until.¶

valid_until

OPTIONAL. [RFC3339] date-time. The delegation MUST NOT be treated as valid at or after this time. No clock-skew tolerance is permitted on this bound.¶

last_updated

OPTIONAL. [RFC3339] date-time at which the policy was last published. It is not decision-affecting ([TRUST-FRAMEWORK] §Terminology).¶

signed_policy

OPTIONAL. String. A signed JWT containing policy members as claims (Section 3.1).¶

crit

OPTIONAL. Array of critical member names, processed as [TRUST-FRAMEWORK] §Critical Members defines.¶

Publishers MUST place crit in the outer, unsigned document, because consumers that do not process signatures cannot see a crit carried only in the JWT. When the document carries signed_policy, publishers MUST also include the same crit as a claim in the signed JWT. A party that can alter the outer document then cannot remove crit (Section 3.1). The DNS record form does not carry crit (Appendix B.2).¶

Consumers MUST ignore unrecognized members, except those named in crit. A document that contains duplicate member names, at the top level or within an authorized_issuers entry object, is malformed and MUST be rejected. The following validation rules apply. A policy failing any of them is malformed:¶

Table 1
Member Required type / structure Additional rule
subject_authority string, required matches the computed Subject Authority
authorized_issuers array of objects, required (MAY be empty for explicit denial) each element has issuer
issuer string, required syntactically valid issuer identifier for the applicable grant profile
tenant string, optional non-empty (see member definition)
subject_identifier_formats array of strings, optional non-empty
valid_from, valid_until, last_updated [RFC3339] date-time, optional valid_from not later than valid_until when both are present
signed_policy string, optional signed JWT as defined in Section 3.1
crit array of strings, optional non-empty; every listed member recognized and implemented, else malformed ([TRUST-FRAMEWORK] §Critical Members)

For OAuth authorization server issuer identifiers, a non-HTTPS URL, a relative URL, or a URL with a query or fragment component is a malformed issuer value ([RFC8414] Section 2).¶

Example:¶

{
  "subject_authority": "example.com",
  "authorized_issuers": [
    {
      "issuer": "https://idp.example.com",
      "subject_identifier_formats": ["email"],
      "valid_until": "2027-01-01T00:00:00Z"
    },
    {
      "issuer": "https://accounts.shared.example",
      "tenant": "example.com",
      "subject_identifier_formats": ["email"]
    }
  ],
  "last_updated": "2026-05-01T00:00:00Z"
}
¶

3.1. Signed Policy

The signed_policy member protects the integrity of the policy members it carries as claims. When the signed JWT contains every decision-affecting member ([TRUST-FRAMEWORK] §Terminology), it provides object-level integrity for the whole document. It follows the signed metadata pattern of [RFC8414] and [RFC9728].¶

A consumer processes signed_policy only when it has an acceptable verification key for it: the key a key= directive pins, or a key configured out of band for the Subject Authority. A consumer without one MUST treat the policy as malformed if crit lists signed_policy or its local policy requires object-level integrity for the Subject Authority. Otherwise, it ignores signed_policy and evaluates the unsigned members. Such a consumer cannot detect a modified outer document, an expired signed_policy, or a replayed older one. The consumer requirements in the rest of this section apply to a consumer that processes signed_policy.¶

The signed_policy value is a JWT [RFC7519] in JWS Compact Serialization [RFC7515] containing policy members as claims. The JWT MUST be signed with an asymmetric algorithm. It MUST contain an iss claim identifying the party attesting to the signed policy claims, and MUST contain iat. It MUST contain exp, which bounds replay of a superseded signed policy (Section 9.5). Consumers MUST reject an expired signed_policy, including a cached copy and during stale-if-error use (Section 7).¶

Consumers MUST reject a signed_policy whose exp is more than 24 hours after its iat. For each Subject Authority, a consumer MUST retain the highest iat it has accepted until the exp of that signed policy. It MUST reject a signed_policy for that Subject Authority with an earlier iat, even after the cached policy itself is gone.¶

The JOSE header SHOULD contain a kid identifying the signing key. The JWT payload SHOULD NOT contain a signed_policy claim. The outer document carries subject_authority and authorized_issuers (Section 3) even when the JWT repeats them.¶

Algorithms: [RFC8725] (JWT Best Current Practices) applies unchanged. In addition, the JWT MUST NOT use a MAC algorithm (HS256/384/512), since a MAC scheme would require sharing the signing key with every Resource Authorization Server. Implementations MUST support ES256 and SHOULD support EdDSA and ES384; RS256 with >=2048-bit keys MAY be supported for compatibility.¶

Per [RFC8725] §3.11 (cross-context confusion), the JWT typ header MUST be issuer-authorization-policy+jwt. This is the media type registered in Section 12.6, with the application/ prefix omitted per the [RFC8725] §3.11 convention.¶

The JWT payload MUST contain subject_authority. When a key= directive pins the verification key, a signature that verifies with that key binds the signer to the Subject Authority, and the JWT iss claim is not further constrained. Otherwise, the JWT iss claim MUST either equal the subject_authority value (for example, acme.example, not https://acme.example) or identify a signing authority that local policy or an applicable Trust Method establishes as controlled by the Subject Authority. Consumers MUST NOT treat a signature by an Assertion Issuer the policy authorizes as proof of Subject Authority authorization unless such a relationship is explicitly established.¶

The verification key MUST be resolved through a channel independent of the one that carried the policy document, and MUST be one of:¶

  • a key whose thumbprint the Subject Authority publishes in a key= directive of its DNS pointer record (Section 4.3). Such a key defeats substitution by the policy host or a shared edge in front of it, but not compromise of DNS, which already selects the policy host. DNSSEC raises that bound.¶

  • a key configured out of band at the consumer, which rests on the consumer's own key-provisioning process.¶

An attacker who controls the publication channel can substitute both the policy and, if the key is fetched over that same channel, the key. Absent an independent channel, the signature provides integrity no stronger than channel control, and consumers MUST NOT rely on it to defend against compromise of that channel.¶

If both unsigned policy members and signed_policy are present, the signed policy claims MUST be used as the policy values for all claims present in the JWT. Unsigned members that are not represented as claims in the JWT MAY be used subject to the normal processing rules for unrecognized members.¶

A conflict exists when a member name appears in both the unsigned outer document and the signed JWT payload AND the two values are not equal as parsed JSON values, ignoring member order and insignificant whitespace; equivalently, when their JSON Canonicalization Scheme [RFC8785] serializations differ. Consumers MUST reject a policy that contains any such conflict. Otherwise, an attacker who can modify the outer document but not the signed JWT could inject visible-but-ignored members that mislead operators or downstream tooling.¶

To require signed_policy processing by all conforming consumers, a Subject Authority lists signed_policy in crit. A consumer that does not implement that processing then rejects the document rather than silently ignoring the signature. Absent a crit entry, signed_policy provides integrity only:¶

  • for consumers that support and verify it;¶

  • where local policy requires signed policy processing; or¶

  • for lookups where a key= directive requires it (Section 4.3).¶

If a consumer's local policy requires object-level integrity through signed_policy, the consumer MUST verify the signed JWT before acting on the policy, and the JWT payload MUST contain every recognized decision-affecting member used by that consumer. The consumer MUST NOT use unsigned recognized decision-affecting members that are absent from the JWT payload. This includes crit. The consumer takes crit from the JWT payload, so removing the outer copy does not remove a critical requirement. An outer crit with no signed counterpart makes the policy malformed. The consumer MUST reject the policy as malformed if any of the following holds:¶

  • signature verification fails;¶

  • the verification key is unacceptable;¶

  • the JWT is malformed;¶

  • the required issuer binding above is not satisfied; or¶

  • the JWT omits a recognized decision-affecting member required for evaluation.¶

4. Publication

A Subject Authority publishes the Issuer Authorization Policy through one of the publication channels defined in Section 4.1. Throughout this document, {A} denotes the Subject Authority rendered as a DNS name (A-label form, Section 4.3).¶

4.1. Publication Channels

This document defines three publication channels. A Subject Authority chooses based on operational constraints; all carry the same document model (Section 3), although the inline form expresses only part of it (Section 9.7).¶

Table 2
Channel DNS form Document Authority binding When to use
1: Inline TXT with issuer= (Section 4.3) None (carried in TXT) DNS control of {A} Common case: authorize an issuer that has its own issuer identifier, with no rich policy; cannot carry tenant (Section 9.7)
2: Pointer TXT with uri=, consumed by canonical lookup HTTPS-hosted JSON under Subject Authority's operational control DNS control of {A} AND TLS on the authority-operated host Rich policy (validity windows, format restrictions, tenant binding) at a controlled origin
3: Dedicated Policy Host TXT with uri= naming the default URL, consumed by the HTTPS-only lookup mode as the opt-in HTTPS-hosted JSON at https://oauth-issuer-policy.{A}/.well-known/oauth-issuer-policy DNS control of {A} (opt-in record) AND of oauth-issuer-policy.{A}, AND TLS on that host Serving Resource Authorization Servers that use the HTTPS-only lookup mode

4.2. Dedicated Policy Host

To serve Resource Authorization Servers that use the HTTPS-only lookup mode, a Subject Authority publishes the policy at the default URL on the dedicated policy host oauth-issuer-policy.{A} (Section 4.4). The opt-in to that mode is a recognized record at _oauth-issuer-policy.{A} (Section 4.3) whose uri= value equals, octet for octet, the default URL built from the lowercase A-label form of {A}. That mode requires such a record before it fetches from the dedicated host (Section 8.2). The same record directs canonical lookups to the same document.¶

The host name alone is not an opt-in. Some domains let untrusted users claim subdomains or serve content on them. On such a domain, an attacker could claim oauth-issuer-policy ([RFC8461] Section 10.3). Subject Authorities whose domains let others claim subdomains SHOULD reserve the oauth-issuer-policy label, in addition to publishing the opt-in record. Nor is every TXT record at _oauth-issuer-policy.{A} an opt-in. An inline record, or a pointer to another host, does not set up the dedicated host.¶

Unlike the apex, the dedicated host can be delegated to a hosting provider (for example, by a CNAME record) without giving that provider control of the Subject Authority's web origin. A key= directive in the opt-in record keeps that provider from altering the policy (Section 9.5).¶

4.3. DNS Record

The Subject Authority publishes one or more DNS TXT records at _oauth-issuer-policy.{A}. Internationalized names are converted to A-labels by the procedure of [TRUST-FRAMEWORK] §Subject Authority Determination before the prefix is prepended. DNS lookup names are formed without a trailing dot for comparison purposes; the wire-format root label is not part of the Subject Authority value.¶

The string segments of a TXT record ([RFC1035]) are concatenated without separator and interpreted as ASCII text. A recognized record (defined below) that contains a non-ASCII octet is malformed, since all defined directive values are ASCII by construction; other records are ignored.¶

A record is recognized if, after optional leading whitespace, it begins with the case-sensitive version token v=oauth-issuer-policy1 followed by end of record, whitespace, or ;. In a recognized record, the version token is followed by optional whitespace and then end of record or a ; separator. Anything else makes the record malformed (Section 5.1). A record that begins with a different version token, such as a future v=oauth-issuer-policy2, is unrecognized, not malformed. Records that do not begin with a supported version token MUST be ignored. A v= directive anywhere other than the start of a recognized record makes the record malformed (Section 5.1).¶

The remainder of a recognized record is a sequence of name=value directives separated by ;. Parsing rules:¶

  • Whitespace (space and horizontal tab) immediately before and after each directive is ignored. A value MUST NOT contain whitespace or non-ASCII characters.¶

  • Directive names are case-insensitive ASCII. Values are case-sensitive and preserved as written.¶

  • A directive splits into name and value at the first =. Subsequent = characters are part of the value. A directive with no = makes the record malformed (Section 5.1). So does a directive whose name does not match the name production below, for example because whitespace precedes the =.¶

  • The value runs to the next ; or end of record. The character ; MUST NOT appear in a value (see the issuer-identifier constraint in Section 3).¶

  • CR, LF, and NUL MUST NOT appear in a value.¶

  • An empty directive (two consecutive ; separators with no intervening name=value) makes the record malformed (Section 5.1).¶

  • Unrecognized directives MUST be ignored.¶

The following ABNF ([RFC5234] with the case-sensitive string extension of [RFC7405]) is normative for the record syntax. A recognized record that does not match record is malformed (Section 5.1).¶

record        = OWS version OWS *( ";" directive ) [ ";" OWS ]
version       = %s"v=oauth-issuer-policy1"
directive     = OWS name "=" value OWS
name          = 1*( ALPHA / DIGIT / "_" / "-" )
value         = *vchar-no-semi
vchar-no-semi = %x21-3A / %x3C-7E   ; VCHAR (%x21-7E) minus ";"
OWS           = *( SP / HTAB )
¶

The following directives are defined:¶

authority=A

REQUIRED. The Subject Authority identifier this record claims to bind. The publisher MUST write this value in A-label (ASCII) form per [RFC5891]. Consumers compare it with the Subject Authority computed from the query name, also in A-label form. The comparison uses the case-insensitive ASCII rules in [TRUST-FRAMEWORK] §Subject Authority Determination. Records whose authority= value does not match are discarded (Section 5). A recognized record containing more than one authority= directive is malformed (Section 5.1).¶

uri=URL

OPTIONAL. An HTTPS URL identifying an Issuer Authorization Policy document. The URL MAY be on a different host than A. MUST use the https:// scheme and MUST NOT contain a fragment component.¶

issuer=ISSUER_URL

OPTIONAL. An Assertion Issuer identifier authorized by the Subject Authority for A. For OAuth authorization server issuer identifiers, the value MUST be an absolute HTTPS URL and MUST NOT contain a query or fragment component. MAY appear multiple times within a record and across records.¶

key=THUMBPRINT

OPTIONAL. The JWK SHA-256 thumbprint [RFC7638], base64url-encoded without padding, of the key that signs the signed_policy of the document named by uri=. That key is the Subject Authority's policy-signing key, not an Assertion Issuer's assertion-signing key.¶

The directive is valid only in a record that carries uri=; in any other record it is malformed. Two distinct key= values across the remaining records let a Subject Authority publish an old and a new key during a rollover; more than two is malformed.¶

When key= is present:¶

  • the fetched document MUST carry a signed_policy whose JWS header carries the signing key in its jwk parameter ([RFC7515] Section 4.1.3);¶

  • the thumbprint of that key MUST equal one of the key= values; and¶

  • the signature MUST verify with that key (Section 3.1).¶

A document that fails any of these checks is malformed, and so Indeterminate (Section 5.1).¶

A key= directive also makes the consumer process the document as if the consumer's local policy required object-level integrity (Section 3.1). When key= is present, the signed JWT MUST contain every decision-affecting member the consumer uses, and the consumer MUST NOT use unsigned decision-affecting members that are absent from it, including crit (Section 3.1).¶

A recognized record MUST contain at least one uri= directive or at least one issuer= directive. Recognized records containing neither MUST be treated as malformed (see Section 5.1).¶

A Subject Authority MUST publish records for at most one version of this mechanism at a time. This document defines only oauth-issuer-policy1.¶

4.4. HTTPS Document URL

The default Issuer Authorization Policy URL is:¶

https://oauth-issuer-policy.{A}/.well-known/oauth-issuer-policy
¶

The URL's path is a well-known URI [RFC8615], and the URL has no userinfo, port, query, or fragment component. A Subject Authority whose form has no DNS-name representation cannot use the dedicated host. This document defines a DNS-name representation only for the email-derived DNS domain. Consumers fetch this URL with an HTTP GET over HTTPS with TLS server authentication and interpret the response body as the JSON document defined in Section 3.¶

A URL obtained from a DNS uri= directive is fetched the same way; TLS authenticates the host serving that URL, not A.¶

Every policy fetch defined here is an outbound fetch subject to [TRUST-FRAMEWORK] §Outbound Fetches; see also Section 9.10.¶

Consumers MUST NOT follow HTTP redirects when fetching a policy, as in MTA-STS ([RFC8461] Section 3.3). A 3xx response other than a 304 validating a held cached policy is Indeterminate (Section 5.1). Hosting the policy elsewhere is expressed only through the uri= pointer, which publishes the delegation in DNS. The response MUST have HTTP status 200 and a media type of application/json or any media type using the structured +json suffix. Media type parameters are ignored. Any other status is classified per Section 5.1.¶

4.5. HTTPS Policy Document Contract

The document fetched from the default URL or from a DNS uri= pointer is the Issuer Authorization Policy defined in Section 3. Consumers MUST NOT interpret any other JSON shape as an Issuer Authorization Policy. Consumers MUST validate the complete policy as a unit: a malformed entry makes the whole policy malformed, not just that entry.¶

The following bounds apply. A response exceeding any bound is classified per Section 5.1.¶

  • Consumers MUST accept a policy document of at least 64 KiB and MAY reject one larger. Publishers MUST keep the document within 64 KiB.¶

  • Consumers MUST accept at least 100 authorized_issuers entries and MAY reject more. Publishers MUST NOT publish more than 100.¶

  • Consumers SHOULD limit JSON nesting depth (the defined document has a fixed shallow structure).¶

  • Fetch timeouts follow [TRUST-FRAMEWORK] §Outbound Fetches.¶

Consumers SHOULD send a conditional request (for example, If-None-Match) when they hold a cached policy, treating a 304 response per Section 5.1. A consumer MUST NOT treat a 304 as renewing a held policy unless:¶

  • the current record's uri= and key= values equal those under which the held policy was retrieved and verified; and¶

  • any signed_policy in the held policy has not expired.¶

The consumer stores those values with the cached policy. If either condition does not hold, it fetches without a conditional request.¶

5. Lookup Procedure

A Resource Authorization Server retrieves the Issuer Authorization Policy for a Subject Authority A with the following steps, the canonical lookup procedure of the domain_authorized_issuer Trust Method. The procedure consults only DNS and the uri= target a DNS record names. The TXT record is the Subject Authority's opt-in: its absence is Negative, and no other channel is consulted. The HTTPS-only lookup mode (Section 8.2) instead fetches the policy only from the dedicated policy host. Section 8.3 covers the choice of mode.¶

  1. Query the DNS TXT resource record set at _oauth-issuer-policy.{A}. Classify the response as:¶

    negative-authoritative

    NXDOMAIN, or NOERROR with an empty answer section or with no recognized records after parsing.¶

    indeterminate

    SERVFAIL, REFUSED, timeout, truncation with no successful retry, or any other failure that prevents a definitive negative result.¶

    affirmative

    NOERROR with at least one recognized record after parsing.¶

  2. If the DNS response is affirmative:¶

    a. Discard recognized records whose authority= directive does not match A under the Subject Authority comparison rules in [TRUST-FRAMEWORK] §Subject Authority Determination. The response is malformed if any recognized record lacks an authority= directive, or if all recognized records are discarded for authority= mismatch. A malformed outcome is Indeterminate (Section 5.1). Finding a record's authority= directive requires only splitting the record into directives at ;. A discarded record is not otherwise validated.¶

    Then validate the remaining recognized records against the directive rules in Section 4.3. A malformed uri= or issuer= value, a record with neither, or any other violation is malformed.¶

    b. If any remaining record contains a uri= directive:¶

    • If more than one distinct uri= value is present across the remaining records, treat as malformed.¶

    • Otherwise fetch the Issuer Authorization Policy from that URL per Section 4.4. All issuer= directives across all records are ignored; step 2a has already applied their validity rules. If a key= directive is present, the document is verified as that directive requires.¶

    c. Otherwise (no uri= present), construct a virtual Issuer Authorization Policy from the records. Its subject_authority is A, and its authorized_issuers has one entry for each distinct issuer= value across the remaining records. Entry order carries no semantics (Section 6). Entries have no tenant, subject_identifier_formats, valid_from, or valid_until. The virtual policy is processed identically to one fetched over HTTPS, except that its cache lifetime is derived from DNS TTLs (Section 7).¶

  3. If the DNS response is negative-authoritative, the lookup is Negative (Section 5.1): the Subject Authority has not published a policy for this mechanism. Consumers MUST NOT fetch the policy from any HTTPS location in this case.¶

  4. If the DNS response is indeterminate, lookup has failed (Indeterminate). Consumers MUST NOT consult another channel, since an attacker who suppresses DNS responses could otherwise force the consumer onto a path the attacker has compromised separately.¶

A Resource Authorization Server that cannot resolve DNS (resolver failure, untrusted resolution path) classifies the lookup as Indeterminate (Section 5.1).¶

5.1. Failure Handling

DAI lookup outcomes map onto the Affirmative, Negative, and Indeterminate lookup states of [TRUST-FRAMEWORK] §Lookup States and Fail-Closed. Those states' requirements apply unchanged, as does the prohibition on falling through to another evidence source ([TRUST-FRAMEWORK] §Multiple Evidence Sources Within a Category).¶

HTTPS responses, when applicable, are 200 OK with a media type of application/json or a +json-suffixed type. The following deterministic conflict rules apply:¶

  • Multiple recognized TXT records containing no uri= directive merge into one virtual policy whose issuer= values form an unordered set (Section 5, step 2c).¶

  • If any remaining record contains a uri= directive, the HTTPS document at the single uri= target is authoritative, and all issuer= directives are ignored. More than one distinct uri= value is malformed (Section 5, step 2b).¶

  • Both lookup modes retrieve the same document: the HTTPS-only lookup mode requires a record whose uri= is the default URL, and that record directs canonical lookup to the same URL (Section 4.2).¶

  • Multiple authorized_issuers entries for the same issuer value but different tenant values are independent authorizations. Entries with tenant do not shadow entries without tenant for the same issuer.¶

  • Only the Subject Authority computed by the extraction procedure for the assertion's Subject Identifier applies. Another Subject Authority's policy cannot grant authority over that subject.¶

A cached Affirmative policy can serve during an Indeterminate live retrieval only within the stale-if-error bound of Section 7. Whether the assertion is then rejected follows [TRUST-FRAMEWORK] §Multiple Evidence Sources Within a Category. An Indeterminate outcome, like a policy that does not authorize the issuer, leaves the subject_namespace_authorization category unsatisfied whatever other methods yield. A Negative outcome, by contrast, lets another method in that category supply evidence.¶

6. Verification

When the domain_authorized_issuer Trust Method is evaluated, the Resource Authorization Server MUST:¶

  1. Determine the Subject Authority from the assertion's Subject Identifier per [TRUST-FRAMEWORK] §Subject Authority Determination. If no Subject Authority results, the assertion is rejected ([TRUST-FRAMEWORK] §Resource Authorization Server Processing, step 5c).¶

  2. Retrieve the Issuer Authorization Policy by applying the procedure in Section 5. Negative and Indeterminate outcomes are handled per Section 5.1.¶

  3. Verify the policy's subject_authority matches the computed Subject Authority. (Virtual policies satisfy this by construction.)¶

  4. Determine whether any entry in authorized_issuers matches. An entry matches when all of the following hold:¶

    a. issuer equals the JWT iss claim under the case-sensitive string comparison of Section 3.¶

    b. If the entry contains a tenant member, its value exactly matches the assertion's top-level tenant claim (in ID-JAG, [ID-JAG] §6.1) under case-sensitive string comparison. An entry with tenant does not match an assertion that lacks the tenant claim. Under any grant profile, an entry without tenant does not match an assertion that carries a tenant claim. Under a grant profile that carries no tenant claim, a tenant claim in the assertion is not attested, so an entry with tenant does not match that assertion.¶

    c. If the entry contains subject_identifier_formats, the Subject Identifier format of the assertion's subject is listed.¶

    d. If valid_from or valid_until are present, the current time is within the validity window (with the skew rules of Section 3).¶

    The Trust Method is satisfied when step 3 succeeds and at least one entry matches under (a)-(d). Entry order in authorized_issuers carries no semantics: the result does not depend on array order or on which matching entry a consumer examines first.¶

If step 2 does not yield a policy, the Trust Method is not satisfied, with the category-level effect stated in Section 5.1. If the Trust Method is not satisfied and, as a result, the cross-category combination rule ([TRUST-FRAMEWORK] §Cross-Category Combination Rule) is not met, the assertion is rejected with the error that [TRUST-FRAMEWORK] §Resource Authorization Server Processing specifies.¶

6.1. Observing Before Enforcing

This document defines no mode in which a published policy is evaluated without being enforced. Under fail-closed evaluation, a namespace with no policy gets no authorization from this Trust Method (Section 5.1), so a first publication withdraws nothing this method granted. A mode that accepted mismatched assertions would admit more issuers than publishing nothing.¶

A Resource Authorization Server introducing domain_authorized_issuer can observe before it enforces. While its Trust Policy does not yet list the method, it evaluates the Trust Method and logs each outcome with its Subject Authority, Assertion Issuer, and match result. Only listed methods are applicable ([TRUST-FRAMEWORK] §Category Applicability), so observation does not affect acceptance. The Resource Authorization Server can share what it observes with affected Subject Authorities out of band. Appendix B sketches a reporting mechanism.¶

7. Caching

Freshness and cache limits for the Issuer Authorization Policy:¶

  • Freshness lifetime.¶

    • The inline form's virtual policy is fresh for the minimum TTL of the records that construct it.¶

    • A policy fetched through a uri= pointer is fresh for the lesser of the pointer record's TTL and the document's HTTP freshness lifetime ([RFC9111]).¶

    • A policy fetched from the dedicated host under the HTTPS-only lookup mode is fresh for the lesser of the opt-in record's TTL and its HTTP freshness lifetime.¶

    A document for which the freshness calculation of [RFC9111] Section 4.2.1 yields no explicit lifetime is fresh for a local default that MUST NOT exceed 1 hour. Consumers MUST NOT treat a cached policy as fresh beyond these lifetimes, except that they MAY apply a minimum freshness lifetime of up to 5 minutes even when a TTL or HTTP lifetime is shorter. That minimum coarsens the timing signal discussed in Section 10.¶

  • Unvalidated DNS. Consumers MUST NOT treat a DNS result that was not DNSSEC-validated as fresh for more than 1 hour, whatever its TTL. A spoofed answer chooses its own TTL (Section 9.4). A result is DNSSEC-validated only if the consumer validated it, or a validating resolver that the consumer reaches over an authenticated channel, such as DNS over TLS or DNS over HTTPS, reported it as validated.¶

  • Steady-state lifetimes. Subject Authorities SHOULD publish records and HTTPS policies with a freshness lifetime of at most 1 hour, reducing it further during an active revocation.¶

  • Absolute ceiling. Consumers MUST enforce an absolute local ceiling of at most 24 hours on the age of any cached policy entry, regardless of TTL or Cache-Control. A cached entry older than the ceiling MUST NOT be used and MUST be re-fetched with an unconditional request.¶

  • Stale-if-error. When a live retrieval is Indeterminate, a consumer MAY continue to use a cached Affirmative policy for at most 1 hour after its freshness lifetime ended, and never past the absolute ceiling. Repeated Indeterminate retrievals do not extend this window ([TRUST-FRAMEWORK] §Fail-Closed Requirements). A successful live retrieval (Affirmative or Negative) replaces the cached entry. The bound keeps an attacker who can sustain denial of service against the publication channel from extending revocation latency toward the absolute ceiling.¶

  • Negative results SHOULD be cached, to bound lookup work under load (Section 9.10). Negative results MUST NOT be cached for longer than the lesser of 1 hour and the lifetime of the DNS answer that produced them. A cache lifetime of 5 minutes is RECOMMENDED for Negative results. The lifetime of the DNS answer is the negative TTL ([RFC2308]) for an NXDOMAIN or NODATA answer. For an answer with records but no recognized record, it is the remaining TTL of the TXT record set. The short cap lets consumers promptly see a Subject Authority's first publication and its recovery from a brief publication-channel takeover. The same cap SHOULD apply to a cached explicit-denial policy (Section 3).¶

  • Indeterminate outcomes MAY be cached for a short period to absorb retry storms. No more than 5 minutes is RECOMMENDED. An Indeterminate cache entry MUST NOT be treated as a policy and never satisfies the Trust Method.¶

After a Subject Authority removes an issuer, consumers can still accept it for up to the sum of:¶

  • the time for the change to reach every authoritative server;¶

  • upstream cache lifetimes: recursive resolvers can serve the old record for its full advertised TTL ([RFC1035] Section 4.1.3), and HTTP caches the old document for its freshness lifetime; and¶

  • one consumer freshness lifetime plus up to 1 hour of stale-if-error use, never beyond the absolute ceiling.¶

Steady-state lifetimes of 1 hour or less, as recommended above, keep this window to a few hours. For a signed policy on a host the Subject Authority does not control, the host can also replay the superseded policy until its exp, at most 24 hours after its iat (Section 3.1).¶

8. Trust Methods

This document defines domain_authorized_issuer as a subject_namespace_authorization Trust Method of [TRUST-FRAMEWORK], registered in the Identity Assertion Trust Methods registry ([TRUST-FRAMEWORK] §Identity Assertion Trust Methods Registry).¶

8.1. domain_authorized_issuer

Under the domain_authorized_issuer method, the Assertion Issuer is acceptable if the Subject Authority identified by the assertion's Subject Identifier authorizes that issuer to assert identities in the Subject Authority's namespace. The method uses this document's publication channels (Section 4.1), lookup procedure (Section 5), and verification rules (Section 6).¶

This Trust Method expresses authorization for either form of multi-tenant Assertion Issuer:¶

  • Per-tenant issuer identifiers, such as https://login.microsoftonline.com/{tenant-id}/v2.0: the case-sensitive comparison of issuer with the JWT iss claim (Section 3) tells tenants on the same host apart, so each authorized tenant is one authorized_issuers entry. If such an issuer also sends a tenant claim, the entry carries the same tenant value (Section 6, step 4b), which only the pointer form can express.¶

  • Shared issuer with a tenant claim: the authorized_issuers[].tenant field binds the authorization to one tenant of the shared issuer, with the security properties in Section 9.9. For example, https://accounts.shared.example serves many tenants and identifies each one with the top-level tenant claim of [ID-JAG] §6.1.¶

{
  "method": "domain_authorized_issuer"
}
¶

With no additional members, the Resource Authorization Server applies the canonical lookup procedure (Section 5). The optional lookup member selects the HTTPS-only deployment variant (Section 8.2).¶

8.2. HTTPS-Only Deployment Variant

Some deployments will not take issuers or a policy location from DNS. They can retrieve the same Issuer Authorization Policy (Section 3) over HTTPS from the Subject Authority's dedicated policy host (Section 4.2), with the DNS record serving as the Subject Authority's opt-in. This is a deployment variant of the DAI mechanism, not a second Trust Method registered by this document.¶

Under this variant, the Assertion Issuer is acceptable if the Subject Authority identified by the assertion's Subject Identifier publishes the opt-in record and, on its dedicated policy host, an Issuer Authorization Policy authorizing the Assertion Issuer.¶

{
  "method": "domain_authorized_issuer",
  "lookup": "https_only"
}
¶

The lookup member is OPTIONAL. If present, its value MUST be https_only.¶

This variant takes no issuers or policy location from DNS.¶

When evaluated, the Resource Authorization Server MUST:¶

  1. Determine the Subject Authority A from the assertion's Subject Identifier per [TRUST-FRAMEWORK] §Subject Authority Determination. If no Subject Authority results, the assertion is rejected ([TRUST-FRAMEWORK] §Resource Authorization Server Processing, step 5c).¶

  2. Query _oauth-issuer-policy.{A} and classify the response as in steps 1 and 2a of Section 5; more than one distinct uri= value, or more than two distinct key= values, across the remaining records is malformed. A negative-authoritative response is Negative. The Subject Authority has opted in to this mode only if a remaining record carries a uri= whose value is exactly the default URL (Section 4.2). If recognized records remain but none does, the outcome is Indeterminate: the Subject Authority has published a policy this mode does not retrieve. An indeterminate or malformed response is Indeterminate. The records' issuer= values are not used.¶

  3. Fetch the Issuer Authorization Policy from the default URL https://oauth-issuer-policy.{A}/.well-known/oauth-issuer-policy per Section 4.4. The Resource Authorization Server MUST NOT take issuers or a policy location from the DNS records: it checks that the opt-in record's uri= is the default URL rather than following it. If the opt-in record carries a key= directive, the document is verified as that directive requires (Section 4.3). Because the Subject Authority has opted in, a dedicated host name that does not exist (NXDOMAIN, or no address records) is Indeterminate (Section 5.1).¶

  4. Classify HTTPS retrieval and document validation outcomes per Section 5.1, which also governs Negative and Indeterminate states.¶

  5. Verify the fetched policy and match the Assertion Issuer against authorized_issuers using steps 3 and 4 of Section 6.¶

Compared to canonical lookup, this mode takes the TXT record's issuers and policy location out of the trust path. It also requires the Subject Authority to provision the dedicated host (Section 4.2). DNS integrity still matters: DNS locates the dedicated host, and its TLS certificate is typically issued through DNS-based validation. But an attacker must also obtain a certificate for the host, not only answer a TXT query (Section 9.3).¶

8.3. Choosing the Lookup Mode

Within domain_authorized_issuer, a Resource Authorization Server selects one lookup mode:¶

  • Canonical DNS-first lookup (Section 5) is the default.¶

  • HTTPS-only lookup (Section 8.2) is an explicit deployment variant for local policy that distrusts issuers or policy locations published in DNS and requires the policy itself to come over TLS-authenticated HTTPS from the dedicated host. It still requires the DNS record as the opt-in.¶

A Trust Policy MUST NOT list more than one domain_authorized_issuer object. A Resource Authorization Server treats a policy that does as listing a malformed Trust Method object ([TRUST-FRAMEWORK] §Resource Authorization Server Processing, step 5a), and rejects the assertion.¶

Resource Authorization Servers MUST NOT evaluate both lookup modes as alternatives for the same assertion. If they did, an attacker who can drive the DNS lookup to indeterminate (resolver denial of service, BGP disruption) could force a fallback to HTTPS-only evaluation, defeating the fail-closed property of the DNS-first lookup.¶

9. Security Considerations

The Issuer Authorization Policy is security-critical: its integrity determines which Assertion Issuers can assert identities in the Subject Authority's namespace.¶

9.1. Namespace Authority Bootstrap

DAI's authority binding is DNS control of the registrable domain and, under the HTTPS-only lookup mode, of the dedicated policy host name under it. As in CAA [RFC8659] and MTA-STS [RFC8461], bootstrap uses an explicit DNS opt-in, a dedicated policy host, and no redirects. Pre-existing DNS risks apply unchanged: typosquatting, expired-domain takeover, and registrar account compromise. The registrable-domain default contains subdomain-takeover impact ([TRUST-FRAMEWORK] §Subject Authority Determination). Identity binding beyond DNS control (legal-entity verification) requires out-of-band mechanisms.¶

In practice, DNS control is also control of the domain's mail. Whoever controls the zone can change its MX records and receive password-reset and account-recovery messages for its addresses. If email-based recovery alone can take over an account at a Resource Authorization Server, an attacker who controls the domain's DNS gains little from this Trust Method that it did not already have. [I-D.hardt-email-verification] makes the same observation about its own DNS delegation. If accounts have stronger recovery, for example phishing-resistant authenticators or administrator-approved recovery, DNS control alone does not take them over. But this Trust Method makes DNS control a direct route to asserting identities in the namespace.¶

9.2. Transport Integrity

HTTPS retrieval integrity rests on TLS server authentication of the policy host; the inline DNS form rests on DNS resolution alone; the pointer form rests on both. Subject Authorities concerned about TLS misissuance are encouraged to publish CAA records [RFC8659] for the policy-hosting domain and to monitor Certificate Transparency logs.¶

9.3. HTTPS-Only Authority Trust Model

The HTTPS-only lookup mode (Section 8.2) substitutes TLS-server authentication for DNS-published authority. Its threat surfaces differ from those of canonical DNS-first lookup:¶

  • DNS-record attacks (Section 9.4) can create or remove the opt-in, or publish a key= that makes retrieval fail (Indeterminate). They cannot choose the policy or its host: the opt-in record's uri= is the default URL, and its issuer= values are not used.¶

  • A domain that lets untrusted users claim subdomains could lose the dedicated host name to an attacker ([RFC8461] Section 10.3). Only a record whose uri= is the default URL opts in, so a domain that publishes only an inline record, or a pointer to another host, is not exposed. A domain that opts in has set up the dedicated host itself (Section 4.2).¶

  • Resolution of the dedicated host still uses DNS. A DNS redirect of that host combined with TLS misissuance substitutes the policy; CAA records and Certificate Transparency monitoring are the primary defenses (Section 9.2).¶

  • The policy's integrity rests on whoever operates the dedicated host (Section 9.5) unless a key= directive pins the policy's signing key.¶

  • Because the dedicated host is a separate name, a Subject Authority whose apex is on a marketing site or CDN it does not control can still participate by provisioning or delegating it.¶

Appendix A.4 discusses the trade-off between the two lookup modes.¶

9.4. DNS Integrity and Compromise

An adversary who can forge DNS responses, through off-path resolver spoofing, authoritative nameserver hijack, registrar account compromise, BGP hijack, or recursive cache poisoning, can substitute the Subject Authority's policy. It can:¶

  • add an attacker-controlled Assertion Issuer to the inline form;¶

  • redirect a uri= pointer; or¶

  • force indeterminate outcomes to benefit a cached attacker-friendly policy.¶

For the pointer form, TLS authentication of the pointed-at host does not mitigate the DNS compromise that selected that host.¶

Absent DNSSEC or an authenticated resolver path, the inline DNS form's integrity is no stronger than the recursive resolver path between consumer and authoritative server. Deployments needing a stronger guarantee SHOULD sign the zone with DNSSEC or use the pointer form with the controls of [TRUST-FRAMEWORK] §Shared Infrastructure and Hosted Well-Known Paths. The inline form's "common case" simplicity (Section 4.1) is an operability tradeoff, not an integrity guarantee.¶

Required framework defenses:¶

  • Consumers MUST discard records whose authority= does not match the queried Subject Authority. This is the wildcard mitigation: a permissive parent-zone wildcard cannot authorize subdomains because consumers reject records lacking the matching authority= directive.¶

  • Consumers MUST verify TLS for any host named by uri=.¶

  • Consumers MUST bound cache lifetimes (Section 7). In the consumer's own cache, a spoofed answer that was not DNSSEC-validated stays fresh for at most 1 hour, and can be served for at most 1 more hour while the live channel is Indeterminate. A poisoned recursive resolver can return the spoofed answer again when the consumer re-queries, so this bound does not cover recursive cache poisoning.¶

  • Consumers performing DNSSEC validation MUST treat validation failure as indeterminate, not negative-authoritative, so that a stripped or broken signature produces a retryable failure rather than a cacheable Negative.¶

  • Subject Authorities SHOULD sign _oauth-issuer-policy.{A} with DNSSEC. Consumers that do not validate DNSSEC SHOULD use a trustworthy resolver path (DNS over HTTPS or DNS over TLS to a vetted resolver).¶

Forged negative answers: a negative-authoritative DNS result is Negative (Section 5). When domain_authorized_issuer is the Trust Policy's only subject_namespace_authorization method, an attacker who spoofs a negative answer can deny service for the namespace but cannot substitute a policy. Negative caching is capped (Section 7), so the denial ends soon after the spoofing does.¶

When the Trust Policy also lists another namespace method, a Negative lets that method supply evidence ([TRUST-FRAMEWORK] §Multiple Evidence Sources Within a Category). A spoofed negative answer can then suppress a published policy that does not authorize the issuer, and let the other method authorize it. In that configuration, only a consumer that authenticates the absence, for example by validating DNSSEC, protects the Subject Authority's denial. Signing the zone does not help a consumer that accepts unvalidated negative answers. The cache cap limits reuse of one forged answer, not an attacker who keeps forging fresh ones.¶

Subject Authorities are encouraged to apply these operational defenses:¶

  • registrar account lock;¶

  • monitoring of the record set and policy document for unexpected changes;¶

  • cross-region and cross-resolver checks to detect localized substitution; and¶

  • avoiding wildcard TXT records in zones participating in this mechanism.¶

9.5. Policy Hosts

The DNS pointer form moves rich policy from DNS into an HTTPS document. General shared-infrastructure risks (multi-tenant CDNs, cache rules, dangling origins) are covered in [TRUST-FRAMEWORK] §Shared Infrastructure and Hosted Well-Known Paths. DAI-specific points:¶

  • The pointer target is trusted fully for the policy contents and is appropriate only when the host is operated for, or otherwise controlled by, the Subject Authority.¶

  • Both the DNS-side authority= directive and the JSON-side subject_authority member MUST match the queried Subject Authority. Each binding is published through a different control path; one missing check would let a compromise of either party claim arbitrary namespaces.¶

  • The uri= pointer is a long-lived trust delegation. Subject Authorities SHOULD reduce DNS TTLs in advance of any planned change of policy host.¶

  • A Subject Authority whose policy host is shared infrastructure, or is operated by a provider, can publish a key= thumbprint (Section 4.3). The host then cannot alter the policy, provided the Subject Authority, not the host, holds the signing key. The host can still withhold the policy. It can also replay an older signed policy whose exp has not passed, to a consumer that has not accepted a newer one (Section 3.1). The 24-hour cap on exp bounds that replay. Removing a hostile host takes a key= rotation or a new uri=.¶

A Subject Authority that hosts its Issuer Authorization Policy on shared infrastructure it does not control end to end SHOULD publish signed_policy with a signing key:¶

  • held outside that infrastructure; and¶

  • resolvable through a channel independent of that infrastructure, such as a key= thumbprint (Section 3.1).¶

Publisher-side criticality does not defend against stripping by an on-path or edge attacker. crit is itself carried in the unsigned document, so an attacker who can strip signed_policy can strip crit with it. A signature defeats such an attacker only if consumers require the signature, through local configuration or a key= directive. Such consumers take crit from the signed JWT (Section 3.1), so the attacker cannot remove a critical requirement either.¶

A consumer configured to require signed_policy for a Subject Authority:¶

  • MUST verify signed_policy before acting on that Subject Authority's policy;¶

  • MUST reject a policy whose signature is missing or invalid; and¶

  • MUST NOT treat a valid TLS connection to a shared edge as sufficient by itself.¶

9.6. Policy Conflicts and Determinism

The lookup procedure (Section 5) resolves the common conflicts among coexisting records or sources deterministically, as specified in Section 5.1. Determinism is a security property. Two verifiers reach the same conclusion about what policy, if any, applies if they:¶

  • receive the same DNS and HTTPS responses;¶

  • use the same Public Suffix List snapshot ([TRUST-FRAMEWORK] §Public Suffix List Versioning); and¶

  • stay within the limits of Section 4.5.¶

An attacker with partial control of one publication channel therefore cannot exploit interpretive ambiguity at the consumer.¶

9.7. Mechanism Limits

  • Authentication. The inline DNS form has no signing mechanism; its authority binding is DNS control. The pointer form relies on DNS selection plus TLS to the selected policy host.¶

  • Scope. A Resource Authorization Server MUST NOT use a matched Issuer Authorization Policy to establish trust for subjects outside that Subject Authority's namespace.¶

  • Inline-form features. The inline DNS form expresses only "issuer X is authorized for Subject Authority A." Deployments needing tenant, subject_identifier_formats, valid_from, valid_until, or explicit denial (an empty authorized_issuers array, Section 3) MUST use the pointer form. A recognized inline record with no issuer= is malformed, so the inline form cannot publish an empty delegation set. Under a grant profile that carries tenant, an inline record that names a shared multi-tenant issuer authorizes none of its tenants (Section 9.9).¶

9.8. Email Local-Part Is Not Authenticated

domain_authorized_issuer evaluates only the email's registrable domain and does not authenticate the local-part. It attests that the Assertion Issuer may assert about emails in the namespace, not that any specific local-part is correct. A Resource Authorization Server that normalizes local-parts (case folding, plus-address stripping, alias collapsing) inherits those assumptions from the Assertion Issuer. An attacker controlling an issuer-accepted alias can then land on a different normalized user. Either disable local-part normalization or verify the local-part through a mechanism outside this document. See also [TRUST-FRAMEWORK] §Scope of Namespace Authorization.¶

9.9. Single-Issuer Multi-Tenant Identity Providers

The Shared Issuer Variant of the End-to-End Example demonstrates the shared-issuer case and its tenant binding. Security points:¶

  • Shared issuers are authorized per tenant. Under a grant profile that carries tenant, an entry without tenant matches only assertions that carry no tenant claim (Section 6). Listing a shared issuer without tenant, including in the inline DNS form, therefore authorizes none of its tenants. A Subject Authority instead authorizes a tenant by listing the (issuer, tenant) pair. Listing (issuer, tenant) pairs relies on a multi-tenant Identity Provider sending the tenant claim, as [ID-JAG] §6.1 requires. A shared issuer that omits the claim anyway would again match an entry without tenant, so Subject Authorities SHOULD list a shared issuer only with tenant.¶

  • Tenant-isolation dependency. The tenant binding is a wire-format expression of trust, not a cryptographic guarantee. The Resource Authorization Server checks the claim against the Subject Authority's chosen tenant value but cannot verify the Identity Provider's tenant isolation. A tenant-isolation defect (cross-tenant minting bug, misconfigured admin operation) defeats the wire-format check. Subject Authorities SHOULD prefer per-tenant issuer identifiers where offered and treat shared-issuer listings as long-lived delegations requiring due diligence on the Identity Provider's tenant-isolation guarantees.¶

  • Grant profiles without a tenant claim. Under a grant profile that carries no tenant claim, such as the generic JWT-bearer grant ([TRUST-FRAMEWORK] §Generic JWT-Bearer Assertion Grant), tenant-scoped authorization is not expressible. An entry with tenant matches no assertion, because the profile does not attest the claim. An entry without tenant matches only assertions that carry no tenant claim. But a shared issuer that omits the claim under such a profile is indistinguishable across its tenants, so the entry matches assertions from every one of them. A Subject Authority relying on a shared multi-tenant Assertion Issuer SHOULD NOT authorize that issuer for such a grant unless per-tenant issuer identifiers are used.¶

9.10. Denial of Service, Amplification, and SSRF

The domain_authorized_issuer lookup can run before the Assertion Issuer is known to be trustworthy. An attacker operating its own authorization server controls the key that verifies the assertion signature. The attacker can therefore drive lookups at will, creating three risks:¶

  • Reflection/amplification and cache exhaustion. A flood of assertions with distinct Subject Authorities (email: x@{random}.example) makes the Resource Authorization Server issue a live DNS query per authority, plus an HTTPS fetch per uri= target. The flood turns the Resource Authorization Server into a request amplifier aimed at third-party DNS and HTTPS infrastructure and fills its cache with distinct-authority entries. Consumers MUST bound lookup work: enforce per-Subject-Authority and global rate limits and bound concurrent outstanding lookups. Consumers SHOULD cache Negative outcomes, and MAY cache Indeterminate outcomes, per Section 7. Consumers MAY impose a maximum number of distinct-authority lookups per unit time, shedding load by treating excess as Indeterminate (fail-closed).¶

  • Server-Side Request Forgery. Every HTTPS policy fetch resolves a host the attacker may control: the uri= target named by a Subject Authority under the attacker's control, or the dedicated host under the HTTPS-only mode. For the dedicated host, the attacker presents an assertion in a namespace it owns and points the host's A/AAAA records at an internal address. The fetch occurs whether or not the body validates, enabling blind internal probing through timing and error differentials. Every such fetch follows the address, timeout, and size rules of [TRUST-FRAMEWORK] §Outbound Fetches. Redirects are not followed (Section 4.4), so the target is always the host the lookup named.¶

  • Cost asymmetry. A single small assertion can cause a full DNS+HTTPS round trip. Consumers SHOULD prefer cached results. Consumers SHOULD NOT perform a live lookup until the client is authenticated and the assertion has passed the cheaper grant-profile validation checks (signature, audience, expiry; [TRUST-FRAMEWORK] §Resource Authorization Server Processing).¶

10. Privacy Considerations

The lookup is verifier-side and per-verification, so it leaks metadata in two directions, and the policy itself is public:¶

  • To the resolver path. A DNS query for _oauth-issuer-policy.{A} exposes to every resolver and on-path observer which Subject Authority {A} is evaluated, and when. It omits the full subject identifier for formats such as email, but the authority plus timing can reveal organizational relationships and login activity. Resource Authorization Servers SHOULD use a privacy-preserving resolver path (DNS over HTTPS or DNS over TLS to a vetted resolver). They SHOULD NOT perform the lookup until it is needed for a concrete verification decision.¶

  • To the Subject Authority. For the dedicated-host and uri= channels, the Subject Authority's own server, or its chosen policy host, observes the Resource Authorization Server's egress IP address and the timing of each fetch. That server or host thereby learns which Resource Authorization Servers the namespace's users authenticate to. The authoritative DNS operator for {A} observes per-lookup timing. An employer acting as its own Subject Authority can thus obtain a near-real-time signal of where employees sign in. Caching (Section 7) is the primary mitigation: it coarsens timing and collapses repeated lookups, so consumers SHOULD cache to the bounds permitted rather than re-fetching per verification. A consumer that applies the minimum freshness lifetime of Section 7 keeps a Subject Authority from observing every sign-in through a very short TTL.¶

  • Policy contents. A published policy is public. It reveals the Subject Authority's Identity Providers, tenant identifiers, and, through valid_until, when its contracts end. Subject Authorities that consider these sensitive publish only what verification needs.¶

11. Operational Considerations

Publishing a DAI record makes DNS and HTTPS control a real-time input to sign-in authorization. A lapse in the record or its host can block legitimate assertions, and an unauthorized change can authorize an attacker. Subject Authorities SHOULD operate the record and any policy host with the same rigor as other sign-in-path infrastructure. Specific guidance:¶

  • Rollout. A namespace without a policy is Negative (Section 5.1), so a first publication withdraws no acceptance that this Trust Method granted. However, at a Resource Authorization Server that also lists another namespace method, the new policy becomes final for the namespace ([TRUST-FRAMEWORK] §Multiple Evidence Sources Within a Category). The policy therefore needs to list every issuer that method accepted. Before publishing, check the issuer list for completeness. Forgotten regional tenants and departing Identity Providers are the usual omissions, and they surface as rejections at such servers. Subject Authorities SHOULD sign the zone with DNSSEC or publish via the pointer form, since every published decision carries the full weight of the publication channel's integrity (Section 9.4).¶

  • Change management and TTLs. Reduce DNS TTLs before any planned change to the record or uri= pointer (Section 9.5). Choose steady-state TTLs that balance propagation speed against resolver load and the consumer cache bounds of Section 7.¶

  • Rotation. To rotate an authorized issuer, publish the new authorized_issuers entry alongside the old one. Remove the old entry only after the old issuer is decommissioned and caches have expired. Overlapping validity windows (valid_from/valid_until) make the transition observable and bounded.¶

  • Signing-key rollover. To roll over a key=-pinned signing key, first publish the new thumbprint beside the old one. Keep signing with the old key until the record carrying both thumbprints has reached every authoritative server, and then for the full TTL the old record advertised, plus any minimum freshness lifetime consumers apply. Recursive resolvers can serve the old record for its whole TTL ([RFC1035] Section 4.1.3), whatever cap a consumer places on its own cache. Then re-sign the policy with the new key, and remove the old thumbprint once cached copies of the policy signed with the old key have expired.¶

  • Withdrawal. To withdraw every authorization, remove the TXT record (Negative) or publish an empty authorized_issuers array (explicit denial). Deleting the policy document instead makes lookups Indeterminate, so consumers can keep using a cached policy within the stale-if-error bound of Section 7.¶

  • Monitoring and zone hygiene. Apply the operational defenses of Section 9.4, including monitoring for unexpected changes and avoiding wildcard TXT records. A wildcard with a non-matching authority= causes recognized-but-discarded records and can push a lookup to Indeterminate.¶

  • Availability. Negative and Indeterminate outcomes fail closed (Section 5.1), so provision the authoritative DNS and any policy host for availability.¶

  • Media type. Serve the policy document with Content-Type: application/json. Static hosts often label a file without an extension application/octet-stream, which consumers treat as Indeterminate (Section 5.1).¶

  • Stable issuer identifiers. Issuer comparison is octet-for-octet (Section 3), so changing an issuer identifier breaks every Subject Authority that lists it until each republishes. Identity Provider operators keep issuer identifiers stable and announce changes ahead of time.¶

  • Many domains. Each registrable domain is a separate Subject Authority (subject_authority names exactly one), so an organization with many domains publishes a record, and for the pointer form a document, for each.¶

  • Users from other namespaces. An assertion about a user whose email is in another organization's namespace (for example, a guest at partner.example signing in through the host organization's Identity Provider) is accepted only if partner.example authorizes that Identity Provider. This follows from namespace authorization and is not a defect.¶

  • Consumer mail domains. This Trust Method is designed for organizational namespaces. A consumer mail provider is unlikely to authorize the Identity Providers its users sign in with elsewhere, so under a Trust Policy whose only namespace method is domain_authorized_issuer, assertions about those users are rejected.¶

Appendix A. Design Rationale

This appendix is non-normative.¶

A.1. Following Existing DNS Authority Patterns

DAI applies the authority-publication pattern that domain owners already use for CAA [RFC8659], MTA-STS [RFC8461], SPF, DKIM, DMARC, and the Email Verification Protocol [I-D.hardt-email-verification]; [TRUST-FRAMEWORK] §Trust Evaluation Rules states how a Resource Authorization Server evaluates such evidence. The name=value record syntax is closest to DMARC's, and DMARC's experience with the organizational-domain boundary informs [TRUST-FRAMEWORK] §Subject Authority Determination. DMARC has since replaced the Public Suffix List with a DNS tree walk ([RFC9989]); see the Public Suffix List discussion there.¶

Unlike CAA (deployment-time), SPF/DKIM (spam-score signal), and MTA-STS (inbound mail), the _oauth-issuer-policy record is consumed during user sign-in (Section 11).¶

Relationship to issuer discovery. WebFinger [RFC7033] and OpenID Connect Discovery tell a client, given a user identifier, where to authenticate the user. DAI tells a verifier, given an assertion, whether its issuer is authorized for the subject's namespace. DAI is published per namespace (not per user), over a DNS channel whose control establishes the authority binding, and carries authorization semantics (validity windows, tenant binding, format restrictions) that a discovery record does not.¶

An earlier proposal, [I-D.sanz-openid-dns-discovery], published a domain's OpenID issuer in a similar DNS TXT record, also for discovery. Client-side discovery layered on DAI is out of scope (Appendix B.6).¶

Relationship to federation-scoped and bilateral mechanisms. SAML federations such as InCommon constrain an Identity Provider's namespaces with the scope metadata extension [SHIBMD], which interfederation services such as eduGAIN [EDUGAIN] carry between federations. There, the federation operator attests scope. DAI's authorization is instead published by the namespace owner, where any verifier can retrieve it.¶

Software-as-a-service providers commonly have a customer prove control of its domain with a one-time DNS challenge and then configure its Identity Provider. FastFed [FASTFED] automates such a relationship, with administrator approval on both sides. Both are bilateral configuration held by the parties to one relationship, not an authorization any verifier can retrieve.¶

Relationship to the Email Verification Protocol. EVP [I-D.hardt-email-verification] also publishes an email domain's issuer in DNS: its relying party resolves _email-verification.{domain} at verification time and rejects a token whose iss does not match. The two records differ in role and in scope.¶

In role, EVP names the issuer that verifies control of an email address, while DAI names the issuers authorized to assert identities in a namespace. A domain that uses one provider for mail and another for single sign-on can rightly give different answers.¶

In scope, EVP allows exactly one issuer, an HTTPS origin with no path, for the raw email domain and for EVP tokens only. DAI, in contrast:¶

  • allows several issuers with full issuer identifiers (including path components);¶

  • binds them to tenants;¶

  • carries authorization constraints; and¶

  • normalizes to the registrable domain.¶

Convergence on a shared record or node name is possible future work (Appendix B.5).¶

A.2. Why a Generic Record Name

The DNS node name, well-known URI suffix, and version token name the document they locate (the Issuer Authorization Policy), not the identity framework consuming it. No member or directive is specific to email or identity assertions; subject_identifier_formats ([RFC9493]) expresses the subject class. The identity-specific machinery lives in [TRUST-FRAMEWORK], whose own well-known URI is identity-scoped for that reason.¶

A future Subject Identifier format with a DNS-publishable Subject Authority reuses domain_authorized_issuer and this record ([TRUST-FRAMEWORK] §Future Extensions), where an identity-scoped name would force a second record at a second DNS name. One per-domain policy surface, extended through registered members, follows the oauth-authorization-server metadata precedent.¶

A.3. Why First-Class Tenant Binding

Shared-issuer multi-tenant Identity Providers (Google Workspace, Auth0 in some configurations, Microsoft Entra B2B in some flows) are common and serve many customer tenants under one issuer URL. Authorizing one without tenant binding would authorize every tenant of that Identity Provider for the namespace, which is almost never the intent. An entry without tenant therefore matches only assertions that carry no tenant claim.¶

The tenant member of an authorized_issuers[] entry binds authorization to the tenant identifier in the top-level tenant claim ([ID-JAG] §3.1, §6.1). The Subject Authority's choice of tenant becomes observable on the wire and verifiable per assertion. The Identity Provider's tenant isolation is still trusted (Section 9.9).¶

A generic claim-matching mechanism was considered instead. First-class tenant was preferred because [ID-JAG] standardizes the claim name, the deployment intent is unambiguous, and the wire format is simpler.¶

A.4. Choosing Between DNS-Published and HTTPS-Only Authority

Canonical DNS-first lookup and HTTPS-only lookup are not strictly ordered by security strength; they trade different risks (Section 9.2, Section 9.3). The inline DNS form resists TLS misissuance; an attacker needs DNS-write or DNSSEC-bypass capability. HTTPS-only lookup resists substitution of the TXT record's issuers or policy location, but a DNS redirect combined with TLS misissuance defeats it. The DNS pointer form is exposed to both.¶

A Subject Authority with strong DNSSEC and weak TLS-issuance controls favors the inline DNS form. A Subject Authority with strong CAA/CT monitoring that prefers to keep its issuer list out of DNS favors the dedicated host and HTTPS-only lookup.¶

A.5. Why a DNS Opt-In and a Dedicated Policy Host

Fetching a well-known URL on the Subject Authority's apex whenever DNS reports no record would make every domain DAI-covered unless it opted out. An attacker who could serve content on a domain's apex could then publish a policy for a domain that never adopted DAI, with no DNS forgery, through:¶

  • a dangling address record;¶

  • a site builder that lets customers place files at arbitrary paths; or¶

  • a takeover of a host the apex redirects to.¶

This document follows MTA-STS [RFC8461] instead. The TXT record is the opt-in in both lookup modes; for the HTTPS-only lookup mode its uri= names the dedicated host's default URL, the policy lives on that host, and redirects are not followed. A host name alone is not an opt-in (Section 4.2). The cost is that a Subject Authority with no control of its DNS cannot participate. The full JSON policy remains available to every Subject Authority through the uri= pointer.¶

Appendix B. Future Extensions

This appendix is non-normative. It sketches deferred features that future specifications may register.¶

B.1. Federation-Bound Issuer Authorization Policy

Where a Subject Authority is a federation Entity, a future extension could authenticate the Issuer Authorization Policy on the dedicated policy host through a digest in the Entity Configuration of the Entity that serves it, using a mechanism such as the proposed Well-Known Binding specification [OIDF-WKB]. The Subject Authority would still author and publish the policy under {A}; federation would add integrity protection, not move namespace authority to a trust anchor. That protection depends on federation enrollment and key control being independent of the domain publication channel. Such an extension would need to define:¶

  • Coverage of the HTTPS-only lookup mode. Inline DNS TXT policies would not be covered, and a uri= pointer only if it names the default URL.¶

  • An exact mapping from Subject Authority {A} to Entity Identifier https://oauth-issuer-policy.{A}, with no path or explicit port, as [OIDF-WKB] requires of any protocol whose peer identifier is not an https URL. A binding keyed to an Entity's own well-known URIs ([OIDF-WKB]) covers documents only on the Entity Identifier's host, and the fixed label keeps any other subdomain Entity from speaking for the registrable domain.¶

  • A trust-anchor parameter on domain_authorized_issuer, separate from any openid_federation.trust_anchors configuration.¶

  • Indeterminate outcomes for a missing binding, digest mismatch, or trust-chain failure, with no fallback to an unbound policy.¶

  • A cache lifetime bounded by the minimum of this document's caching limits, the Entity Configuration's exp, and the trust chain's expiry.¶

  • Revocation handling: overlapping old and new digests lets an origin attacker replay a policy that still authorizes a revoked issuer. Emergency revocations should omit that overlap, as [OIDF-WKB] specifies for any replacement that is a revocation, while accounting for residual exposure from cached Entity Configurations.¶

B.2. Critical Directives for the DNS Record Form

In the JSON document, an extension can mark a new decision-affecting top-level member critical with crit (Section 3), and already-deployed consumers honor it. An extension that narrows authorized_issuers entries defines a top-level member for publishers to list in crit, since crit does not reach entry members (Section 12.5).¶

The DNS record form has no per-directive criticality mechanism. Its version token (Section 4.3) prevents misinterpretation of incompatible future syntax by making unrecognized versions ignored. As a result, a Subject Authority that publishes only an unrecognized version is Negative to an older consumer. A future extension that needs per-directive fail-closed semantics in the DNS form would define a crit= directive and its recognition rules.¶

B.3. Evaluation Reports

A Subject Authority learns which assertions Resource Authorization Servers reject for its namespace only out of band (Section 6.1). A future extension can define aggregate reporting like DMARC's [RFC9990]: a policy member naming a reporting endpoint, a report format (observed issuers, match and mismatch counts, time window), and delivery requirements. It is deferred because reporting carries privacy and abuse considerations that deserve their own document: a reporting endpoint learns which Resource Authorization Servers a namespace's users sign in to, concentrating the metadata discussed in Section 10.¶

B.4. Audience-Scoped Delegations

An authorized_issuers entry does not limit which Resource Authorization Servers accept the issuer's assertions, so a compromised but listed issuer can assert the namespace's users to any consumer ([TRUST-FRAMEWORK] §Scope of Namespace Authorization). A future permitted_audiences entry member would let a Subject Authority bound that blast radius by enumerating or pattern-matching audiences. It is deferred because audience identifiers are grant-profile-specific and the open-world deployments this mechanism targets have no enumerable audience set. A design likely needs audience patterns and a rule for its interaction with the assertion's aud claim.¶

B.5. Email Verification Protocol Bridge

The Email Verification Protocol [I-D.hardt-email-verification] defines a DNS TXT record at _email-verification.{domain} whose iss= value names an authorized issuer for the namespace. A future Trust Method (provisionally email_verification_dns) could let a Resource Authorization Server honor those records without an _oauth-issuer-policy record. It would add:¶

  • a second record format;¶

  • a different issuer-identifier shape: a bare hostname, yielding an HTTPS origin with no path; and¶

  • different email-domain semantics: the email's raw domain part rather than the registrable domain.¶

It is deferred for that cost, and because [I-D.hardt-email-verification] progresses on its own timeline. Meanwhile, a deployment can publish both an _oauth-issuer-policy record satisfying domain_authorized_issuer and its existing _email-verification record for other consumers.¶

B.6. Assertion Issuer Discovery (Client-Side)

The same DAI records could let a client discover, before any assertion exists, which Assertion Issuer is authoritative for a subject identifier's namespace. Given alice@acme.example, a client can:¶

  • query _oauth-issuer-policy.acme.example;¶

  • retrieve the Issuer Authorization Policy; and¶

  • resolve an authorized issuer's authorization server metadata to find its token endpoint.¶

Entry order carries no semantics, so a profiling document would specify issuer selection. The use case is deferred because:¶

  • It adds a second mental model: back-channel discovery versus verification at token exchange.¶

  • Its query reveals the Subject Authority to DNS resolvers and to the policy host before any user interaction, a privacy concern distinct from verification.¶

  • It is not on the Resource Authorization Server implementer's critical path.¶

A future specification can profile it with privacy guidance and integration with OAuth Authorization Server Metadata [RFC8414] and OpenID Connect Discovery [OIDC-DISCOVERY].¶

Appendix C. DNS-Based Domain-Authorized Issuer End-to-End Example

This appendix is non-normative.¶

The Subject Authority publishes a DAI record, an Assertion Issuer issues an identity assertion, and the Resource Authorization Server uses the record to verify that the issuer is authorized for the asserted namespace.¶

C.1. Cast

  • Subject Authority, acme.example. A small organization that owns its DNS but does not operate an authorization server capable of issuing identity assertions.¶

  • Assertion Issuer, https://idp.example.net. A managed authorization server service acme.example has contracted with.¶

  • Resource Authorization Server, https://api.resource.example.¶

  • Client, a backend SaaS integration.¶

  • End user, Alice (alice@acme.example).¶

C.2. Publication

The Subject Authority publishes a single DNS TXT record:¶

_oauth-issuer-policy.acme.example. IN TXT ( "v=oauth-issuer-policy1;"
    "authority=acme.example;"
    "issuer=https://idp.example.net" )
¶

The quoted segments form one record (Section 4.3). No HTTPS endpoint is operated on acme.example.¶

The Resource Authorization Server publishes a Trust Policy that lists domain_authorized_issuer with canonical lookup:¶

{
  "resource_authorization_server": "https://api.resource.example",
  "authorization_grant_profiles_supported": [
    "urn:ietf:params:oauth:grant-profile:id-jag"
  ],
  "subject_identifier_formats_supported": ["email"],
  "issuer_trust_methods": [
    {
      "method": "domain_authorized_issuer"
    }
  ]
}
¶

C.3. Issuance and Token Request

  1. The Client, configured outside DAI to use https://idp.example.net for Acme users, authenticates Alice at that issuer and requests an ID-JAG with audience https://api.resource.example carrying Alice's email:¶

    {
  "iss": "https://idp.example.net",
  "aud": "https://api.resource.example",
  "exp": 1780166400,
  "iat": 1780166100,
  "jti": "5a17...",
  "sub": "user-9241ab",
  "email": "alice@acme.example",
  "email_verified": true
}
    ¶

  2. The Client posts to the Resource Authorization Server's token endpoint with private_key_jwt client authentication:¶

    POST /token HTTP/1.1
Host: api.resource.example
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&assertion=eyJhbGciOiJSUzI1NiIs...
&client_assertion_type=
urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=eyJhbGciOiJFUzI1NiIs...
    ¶

    Line breaks in the request body are for display only.¶

C.4. Verification (Resource Authorization Server Side)

  1. The Resource Authorization Server validates private_key_jwt client authentication, then the ID-JAG: signature (via https://idp.example.net/.well-known/openid-configuration JWKS), aud, exp, iat, replay protection.¶

  2. The Resource Authorization Server evaluates the domain_authorized_issuer Trust Method.¶

    a. It extracts the Subject Authority from the top-level email claim (with email_verified=true): acme.example.¶

    b. Applying the canonical lookup procedure (Section 5), it queries DNS TXT at _oauth-issuer-policy.acme.example and parses the record published above.¶

    c. The authority=acme.example directive matches and no uri= is present, so it constructs a virtual policy for acme.example with one authorized_issuers entry for https://idp.example.net.¶

    d. The ID-JAG iss value https://idp.example.net matches the single entry's issuer value. Verification succeeds.¶

  3. The Resource Authorization Server issues an access token in the response body.¶

C.5. Migration Variant: Pointer Form

If acme.example later wants to express validity windows, format restrictions, or tenant binding, it can switch to the pointer form without changing any consumer behavior:¶

_oauth-issuer-policy.acme.example. IN TXT ( "v=oauth-issuer-policy1;"
    "authority=acme.example;"
    "uri=https://oauth-issuer-policy.acme.example"
    "/.well-known/oauth-issuer-policy" )
¶

and publish the richer JSON document at that URL, the default URL on its dedicated policy host, which also serves Resource Authorization Servers that use the HTTPS-only lookup mode:¶

{
  "subject_authority": "acme.example",
  "authorized_issuers": [
    {
      "issuer": "https://idp.example.net",
      "subject_identifier_formats": ["email"],
      "valid_until": "2027-05-30T00:00:00Z"
    },
    {
      "issuer": "https://idp-backup.example.net",
      "subject_identifier_formats": ["email"]
    }
  ],
  "last_updated": "2026-05-29T00:00:00Z"
}
¶

C.6. Shared Issuer Variant: Multi-Tenant Identity Provider

The example above uses an issuer identifier dedicated to Acme. Some Identity Providers serve every tenant under one shared issuer (for example, https://accounts.shared.example) and distinguish tenants by the ID-JAG top-level tenant claim ([ID-JAG] §6.1). For these, the authorized_issuers[].tenant member binds the authorization to one tenant of the shared issuer.¶

Suppose Acme's tenant identifier at the shared issuer https://accounts.shared.example is acme-corp. Acme publishes the pointer form, pointing at this JSON:¶

{
  "subject_authority": "acme.example",
  "authorized_issuers": [
    {
      "issuer": "https://accounts.shared.example",
      "tenant": "acme-corp",
      "subject_identifier_formats": ["email"]
    }
  ],
  "last_updated": "2026-05-29T00:00:00Z"
}
¶

Verification adds one check to the simple flow: besides matching iss, the Resource Authorization Server requires the ID-JAG's top-level tenant claim to equal "acme-corp". An assertion from https://accounts.shared.example with a different tenant value (or no tenant) does not match this entry (Section 9.9).¶

C.7. Failure Variants

  • A DNS SERVFAIL at _oauth-issuer-policy.acme.example is classified as indeterminate (Section 5.1). The Resource Authorization Server consults no HTTPS location; it returns invalid_grant.¶

  • If acme.example published no TXT record, the lookup would be Negative and the assertion rejected, even if a document existed at the default URL on oauth-issuer-policy.acme.example: the TXT record is the opt-in.¶

  • A wildcard record at *.acme.example, which DNS uses to answer a query for _oauth-issuer-policy.acme.example when no record exists at that name, would have to carry authority=acme.example to be accepted. A wildcard with a different authority= is discarded; if no other recognized record remains, the response is malformed (Indeterminate) and the assertion is rejected.¶

  • If acme.example rotates its authorized Assertion Issuer, a Resource Authorization Server holding a cached virtual policy can keep accepting assertions from the old issuer until its cache expires. Short DNS TTLs during rotation shorten that window, and consumers enforce a local cache ceiling per Section 7.¶
